# 后端开发规范

## 1. 技术约定

- 使用 NestJS 与 TypeScript。
- 数据库使用 PostgreSQL。
- 沿用仓库当前使用的 ORM、校验库、日志库和异常处理机制。
- 使用 pnpm 管理依赖。
- 优先使用现有依赖，不随意引入新框架。
- 以仓库实际脚本执行测试、类型检查和构建。

## 2. 模块设计

- 按业务职责划分 NestJS 模块。
- 控制器处理 HTTP 请求与响应。
- 服务层负责业务逻辑。
- 数据访问逻辑遵循项目既有架构。
- DTO 用于定义和校验外部输入。
- 共享模块只放置确实需要复用的能力。
- 避免循环依赖和跨模块直接访问内部实现。

## 3. 输入校验

- 对外部输入进行类型与业务校验。
- 校验必填字段、格式、长度、范围和枚举值。
- 不信任客户端传来的用户身份或权限信息。
- 数据库约束应作为重要的数据完整性保障。
- 不得仅通过 TypeScript 类型替代运行时校验。

## 4. 身份认证与权限

- 沿用项目现有认证机制。
- 在服务端执行必要的身份认证和资源级授权。
- 对列表、详情、修改和删除等操作分别检查权限。
- 避免越权访问其他用户的数据。
- 敏感操作应按业务要求记录审计信息。
- 不在日志中记录密码、访问令牌或不必要的敏感数据。

## 5. 数据库访问

- 优先使用参数化查询或 ORM 提供的安全查询方式。
- 避免不必要的全表扫描和重复查询。
- 根据查询模式评估索引。
- 对需要保持一致性的多步操作使用适当的事务。
- 考虑并发修改和唯一性冲突。
- 数据库迁移应可审查，并明确部署影响。

## 6. API 规范

- 遵循已批准的 API 契约。
- 统一请求参数、响应结构和错误格式。
- 明确分页、筛选、排序和默认值。
- 对新增或修改接口分析向后兼容性。
- 不通过隐藏错误或伪造成功响应处理异常。

## 7. 测试规范

- 单元测试覆盖关键业务逻辑和边界条件。
- 集成测试验证 API、数据库和模块协作。
- 测试权限不足、输入错误和资源不存在等情况。
- 数据库测试应考虑数据隔离和清理。
- 不得仅依赖 Mock 验证数据库集成正确性。
- 执行命令必须以仓库实际配置为准。

## 8. 禁止事项

- 未经批准执行破坏性数据库操作。
- 未经确认修改公共接口契约。
- 在代码中硬编码密钥或生产环境凭证。
- 吞掉异常并返回虚假成功结果。
- 删除失败测试以使流水线通过。
- 引入未经评估的重大依赖。
