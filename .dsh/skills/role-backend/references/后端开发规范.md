# 后端开发规范

## 1. 模块职责

| 部分       | 职责                                                             |
| ---------- | ---------------------------------------------------------------- |
| Module     | 组装模块内 Controller、Provider，并显式公开允许复用的 Provider。 |
| Controller | 适配 HTTP 输入、调用用例并返回契约定义的结果；不承载业务规则。   |
| Service    | 实现业务用例、规则和必要的协作流程。                             |
| DTO        | 表达外部输入/输出；输入 DTO 配置运行时校验。                     |
| Entity     | 表示持久化模型，不直接作为默认 API 响应。                        |
| Repository | 封装数据访问；按现有模式或实际复杂度决定是否单独设置。           |

按业务能力组织模块，不按数据库表机械拆分。纯转发或健康检查等简单端点不必为满足层数增加空 Service。数据访问可以沿用现有 Service 注入方式；只有项目已有约定、查询复杂或需要隔离数据源时，才增加自定义 Repository。

## 2. 模块目录与复用

模块应把相关 API、用例、持久化模型及测试收在同一业务范围内。具体目录遵循仓库现状，参考 `接口与数据库示例.md`。

- DTO 是传输边界模型；不要用 DTO 替代内部领域类型，也不要将 Entity 当作公共契约。
- 多个文件共用的模块内类型放在模块自己的 `types/`；单文件专用类型留在原文件。
- 多个文件共用的纯函数放在模块自己的 `utils/`；业务规则留在 Service，不把 `utils/` 变成杂项目录。
- 确认多个模块需要同一能力后，再按需创建 `apps/backend/src/common/types/` 或 `apps/backend/src/common/utils/`；保留一份实现，通过公开导出复用。
- 模块间通过显式导出的 Provider 或稳定契约协作，不引用对方私有 Service、Repository、DTO 或 Entity；避免循环依赖。

## 3. API、输入与权限

- 请求、响应和错误语义遵循已批准的 API 契约；变更前评估兼容性并同步相关 Agent。
- 所有外部输入都要有运行时校验；TypeScript 类型或 DTO 装饰器本身不等于运行时校验，须确认应用入口或路由管线实际启用校验。
- 服务端校验身份和资源权限，不信任客户端传入的用户身份、所有者或权限字段。
- 按契约处理分页、筛选、排序、重复请求及并发语义，不为所有接口强加同一行为。
- 响应只包含契约允许公开的数据；异常不得泄露堆栈、密钥或内部细节。

## 4. 数据与迁移

- 沿用项目现有的数据访问方式。执行数据迁移前确认已配置的迁移工具、历史记录和回滚路径；未配置时先与架构 Agent 确定可执行方案，不得假定脚本或流程已存在。
- 由业务不变量决定唯一约束、关联、索引和删除策略；数据库约束用于兜底数据完整性。
- 多步写入必须保持原子一致时使用事务；同时评估并发冲突和幂等要求。
- 修改结构时检查已有数据、所有使用方、部署顺序及回滚或恢复方式。
- 已应用的历史迁移不得随意改写；破坏性变更和生产迁移须经授权。
- 大表、锁表或不可逆变更应评估分阶段发布、备份与恢复方案。

## 5. 安全与日志

- 不在源码、响应或日志中记录密码、令牌、密钥及不必要的个人数据。
- 查询使用项目现有安全方式，避免拼接不可信输入。
- 敏感操作按需求记录审计信息；日志不替代授权检查。

## 6. 测试

- 单元测试验证业务规则、边界和失败分支。
- 集成或接口测试验证模块协作、权限和持久化行为。
- 影响事务、约束或查询语义时，用真实数据访问测试关键行为，不能只靠 Mock。
- 测试应关联需求验收标准；使用仓库中实际配置的命令。
- 未执行、失败或受环境阻塞的验证必须如实报告。
