# 接口与数据库示例

本文件是设计和实现参考，不替代需求、架构契约或项目现有规范。示例结构不代表必须新建所有目录；脚手架生成的 CRUD 方法也不等于实际业务需求。

## 1. 业务模块结构

```text
modules/<domain>/<feature>/
├─ <feature>.module.ts
├─ <feature>.controller.ts       # 有 HTTP 接口时
├─ <feature>.service.ts          # 有业务用例时
├─ dto/                           # 有外部传输模型时
├─ entities/                      # 有持久化模型时
├─ types/                         # 多个模块内文件共用的类型
├─ utils/                         # 多个模块内文件共用的纯函数
├─ repositories/                  # 项目约定或数据访问复杂时
└─ *.spec.ts                      # 按项目现有测试组织方式
```

目录按实际需要创建。模块按业务能力划分；类型、工具和 Repository 不需要一开始全部建立。模块内共享的类型和纯工具留在模块目录；确有跨模块复用时，再按需创建 `apps/backend/src/common/types/` 或 `apps/backend/src/common/utils/`，避免复制实现。

## 2. 职责与调用方向

```text
HTTP 请求
  -> Controller（解析并适配传输边界）
  -> Service（执行业务用例）
  -> 现有数据访问方式（读写持久化数据）
```

- Controller 不决定业务规则，不直接绕过用例层操作其他模块的数据。
- Service 组合业务规则、权限条件和数据访问；简单无业务端点可保持轻量。
- DTO 负责外部请求校验；响应按契约返回，不默认序列化 Entity。
- Repository 是可选的数据访问边界，不要求每个 Entity 配一个。
- Module 负责装配本模块 Provider；只有明确允许复用的 Provider 才导出。
- 模块 A 调用模块 B 时，经 B 显式导出的 Provider 或稳定契约协作，不导入 B 的私有实现。

## 3. API 契约核对

每个新增或修改的接口按需说明：

| 项目 | 需要明确的内容                                   |
| ---- | ------------------------------------------------ |
| 标识 | 需求编号、验收标准、方法和路径                   |
| 权限 | 是否需要认证、允许的主体及资源级授权规则         |
| 请求 | 路径/查询/请求体字段、格式、范围和校验失败语义   |
| 响应 | 成功状态、返回字段、分页或空结果行为             |
| 错误 | 可预期的错误类型和对外信息；不得泄露内部细节     |
| 语义 | 数据副作用、重复请求、并发和兼容性要求（适用时） |
| 验证 | 关联测试及正常、边界、拒绝访问和失败场景         |

契约有未定的产品行为时先澄清，不根据脚手架当前响应或实现补造规则。

## 4. 数据结构变更核对

新增或修改持久化结构时，记录：

- 业务用途、字段类型、可空性、默认值和数据来源。
- 唯一、关联、检查约束以及与查询模式相符的索引。
- 更新、删除和软删除语义。
- 现有数据如何兼容或回填。
- 部署顺序、应用耗时、锁表风险及回滚/恢复方案。
- 受影响的接口、模块、报表和测试。

只在多步写入必须原子提交时使用事务。并发、幂等、锁和索引依据业务不变量与访问模式决定，不作为每张表的固定清单。

## 5. 高风险迁移参考

当一次变更无法兼容旧代码或旧数据时，评估分阶段迁移：

1. 先新增兼容结构，不立即删除旧字段或旧接口。
2. 按可重试、可观测的方式迁移已有数据。
3. 切换读写方，并验证新旧数据一致性。
4. 确认所有使用方完成切换后，再移除旧结构。

不适合分阶段的情况，需写明停机窗口、备份、恢复步骤和审批要求。不得在未授权环境执行破坏性迁移。
