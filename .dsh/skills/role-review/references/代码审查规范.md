# 代码审查规范

## 审查尺度

目标是确认变更改善了整体代码健康，而不是追求个人偏好的写法。优先审查本次差异；只有影响调用方、数据、权限或其他高风险边界时才扩大范围。小而聚焦的变更更容易验证和维护。

先核对需求、验收标准和设计，再检查实现。重点看：

1. **行为**：正常、异常、边界和权限路径是否符合预期；是否改变未授权的产品行为。
2. **设计**：职责、依赖和接口是否清楚；是否有重复实现、过度复杂或不必要的抽象。
3. **可靠性**：状态、并发、事务、资源和错误处理是否可能造成错误结果或数据不一致。
4. **安全**：仅对相关路径检查输入来源、校验、认证授权、敏感数据、注入、文件/命令操作及信任边界；关注业务流程绕过和越权。
5. **兼容性**：接口、数据结构、配置、迁移和调用方是否受影响；变更是否有回滚或兼容方案。
6. **测试**：测试是否断言用户可观察的结果，覆盖关键边界和回归路径；调用成功本身不等于行为正确。
7. **交付影响**：相关文档、依赖、配置、构建或部署方式是否需要同步更新。

不相关的检查项标记为不适用，不要求每次做全量安全审计。高风险变更可扩大到相关完整流程；常规变更以差异审查为主。自动化检查用于辅助，不代替对业务逻辑和安全边界的人工判断。

## 发现问题

先确认问题能由代码、测试或可复现步骤支持。每项发现单独描述：

- **严重程度**：阻塞 / 高 / 中 / 低。
- **位置与证据**：文件和行号，以及触发条件或相关代码事实。
- **影响**：谁会在什么条件下受到什么影响。
- **建议**：修复方向及需要补充的验证。

严重程度按影响判断：

- **阻塞**：严重安全风险、关键数据损坏或主要功能不可用。
- **高**：关键需求不满足、主要流程错误或重大回归风险。
- **中**：特定场景下的功能缺陷或明显维护风险。
- **低**：范围有限且不阻塞交付的问题。

有疑点但证据不足时列为待确认，不按确定缺陷定级。风格建议和轻微改进不得伪装成阻断项。

## 参考来源

以下原则经裁剪后用于本项目，不照搬外部组织的审批和发布制度：

- [Google Engineering Practices：Code Review Standard](https://google.github.io/eng-practices/review/reviewer/standard.html)：以整体代码健康改善作为审查尺度，避免为完美主义阻塞有效变更。
- [Google Engineering Practices：Code Review](https://google.github.io/eng-practices/review/)：关注设计、正确性、复杂度、测试、文档和变更范围。
- [Microsoft SDL：安全开发和操作概述](https://learn.microsoft.com/zh-cn/compliance/assurance/assurance-security-development-and-operation)：采用独立审查，核对设计要求、功能与安全验证、文档、配置和依赖。
- [OWASP Secure Code Review Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Code_Review_Cheat_Sheet.html)：采用风险驱动的差异审查，关注数据流、输入、权限和信任边界。
