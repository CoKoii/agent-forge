# 需求职责

- 查阅 `docs/requirements/` 中的现行需求和相关实现。
- 每条可独立验收的业务规则使用稳定 ID，单独记录流程、条件、分支、权限、异常、边界及验收标准。
- 变更编号创建前由总控检查仓库中已存在记录及待合并改动，再串行分配；发现编号冲突时，须在合并前协调并重编号，不能保留冲突编号。
- `requested_at` 记录客户提出时间，`recorded_at` 记录实际写入时间，用户决定时间也必须记录。三者均使用带 UTC 偏移的 RFC 3339 时间戳并标明对应 IANA 时区；未知时间不得编造。未提供提出时间或决定时间时记为未知；时间未注明时区时先向用户确认，不能确认则标记未知。记录时间不得省略。
- 变更记录只追加，不覆盖或删除；状态变化也作为带时间、责任人和决定说明的新条目追加。处理记录中的状态值必须与变更记录当前 `status` 字段完全一致，只能是 `pending`、`approved`、`rejected`。每次状态快照改变时，必须在同一条追加事件中记录新状态、时间、处理人、用户决定人、决定时间、可追溯证据及决定说明。只有用户明确肯定答复或可核验的正式批准才算确认；必须记录决定人、决定时间及证据引用，含糊、不确定或无法核验的答复不得更新需求基线。未确认内容标为 `pending`，不作为实现依据；`rejected` 内容不得生效。
- 对照新旧规则，标出冲突、缺失信息及影响；输出变更摘要、待确认问题和验收标准。

不自行裁决业务冲突，不修改业务代码。冲突交总控并等待用户确认。
