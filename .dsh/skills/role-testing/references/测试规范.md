# 测试规范

## 一、选择测试范围

根据需求、改动边界和失败影响选择必要验证，不要求每个任务都覆盖所有层级。

- **单元测试**：验证独立函数、业务规则、校验和错误处理。
- **集成测试**：验证模块、API、权限、数据读写或事务协作。
- **端到端测试**：验证关键用户流程；仅在项目已有相应配置时执行。未配置时说明缺口，不得声称已覆盖。
- 测试文件名被 runner 匹配，不代表相应测试框架或运行环境已配置；检查实际执行方式后再报告覆盖。

按功能适用性考虑正常输入、非法输入、边界、空数据、权限、资源缺失、重复请求、并发、依赖失败和回归，不必机械地覆盖每一项。

## 二、测试位置与复用

- 将测试放在仓库现有测试组织中，优先靠近被测模块；遵循当前识别的文件模式，如 `.spec.ts` 或 `.test.ts`。
- Helper 先留在所属测试或模块内；只有被多个独立测试范围真实复用时，才提升到共享位置。
- 测试应可重复执行，不依赖顺序或不稳定的外部状态；测试数据应隔离并可清理。
- 断言用户可观察的行为和结果。仅断言服务或依赖已定义属于装配冒烟测试，不能单独作为业务验收证据。

## 三、需求追踪

- 功能测试以相关 AC 为验证依据；发现 AC 缺失或不明确时，报告缺口，不代替产品决策。
- 需要持久追踪的测试场景按 `.dsh/skills/role-requirements/references/编号与追踪规则.md` 分配 `TC-MODULE-NNN`，并关联一个或多个 AC。
- TC 表示可追踪的场景，不等于测试代码中的每个 `it`、`test` 或断言。记录 TC 与实际测试文件/场景的映射。
- 纯技术维护或无正式需求编号的验证，记录任务范围即可，不编造需求编号。

示例（仅展示追踪关系，不代表仓库已有该测试）：`TC-USER-001` -> `AC-USER-001` -> 用户资料更新场景。报告中再记录实际测试文件和用例名。

## 四、执行与结论

1. 检查对应 workspace 的 `package.json`、测试配置和现有用法。
2. 选择与改动范围匹配的命令；不要假设所有 workspace 共用独立脚本。
3. 先运行目标测试，再按风险运行必要回归。
4. 记录真实执行命令和结果；未执行、跳过、阻塞及未覆盖须区分说明。

当前仓库的统一入口是根目录 `pnpm test`，执行 `vp test run`；根 `vite.config.ts` 识别 `*.test.ts`、`*.spec.ts` 和 `*.e2e-spec.ts`。工作区脚本或配置变更后，以实际配置为准。

结果状态：

- **通过**：测试实际执行并满足断言。
- **失败**：测试实际执行但未满足预期。
- **跳过**：测试存在但本次未执行。
- **阻塞**：环境或依赖问题导致无法验证。
- **未覆盖**：没有适用测试验证相关行为。

测试通过不等于代码审查通过或项目整体验收通过。
