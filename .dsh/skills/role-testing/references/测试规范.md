# 测试规范

## 一、测试层级

### 单元测试

验证独立函数、业务逻辑、组件或服务的行为。

优先覆盖：

- 关键业务规则。
- 输入校验。
- 边界条件。
- 错误处理。

### 集成测试

验证模块之间、API 与业务服务之间，以及后端与数据库之间的协作。

优先覆盖：

- API 请求与响应。
- 权限校验。
- 数据读写和事务。
- 数据约束及异常处理。

### 端到端测试

使用 Playwright 验证完整用户流程。

优先覆盖：

- 登录及权限相关流程。
- 关键业务操作。
- 表单提交。
- 关键页面状态与错误反馈。

不要求每个功能都编写所有层级的测试，应根据风险和项目结构选择。

## 二、测试场景

根据功能适用性检查：

- 正常输入。
- 非法输入。
- 缺少必填字段。
- 边界值。
- 空数据。
- 未授权访问。
- 资源不存在。
- 重复请求。
- 并发或数据一致性问题。
- 网络或依赖服务失败。
- 回归影响。

## 三、测试追踪

每个正式测试用例至少关联一个验收标准。

示例：

- 需求：REQ-USER-001
- 业务规则：BR-USER-001
- 验收标准：AC-USER-001
- 测试用例：TC-USER-001

一个验收标准可以关联多个测试用例，一个测试用例也可以验证多个相关验收标准。

## 四、测试实现要求

- 优先沿用项目已有的测试框架、目录和命令。
- 测试应可重复执行，避免依赖不稳定的外部状态。
- 对时间、随机值和外部服务采用合理的隔离策略。
- 集成测试应妥善管理测试数据。
- 不依赖测试执行顺序。
- 不使用无意义的断言来制造覆盖率。
- 不为追求覆盖率而忽略业务风险。

## 五、执行要求

1. 先检查 `package.json` 和实际测试配置。
2. 选择与改动范围相匹配的测试命令。
3. 修复后运行相关测试。
4. 根据影响范围运行必要的回归测试。
5. 记录命令、执行结果和环境限制。

不得假设所有工作区都使用相同测试命令。

## 六、测试结论

- 通过：测试实际执行且满足断言。
- 失败：测试实际执行但未满足预期。
- 跳过：测试存在，但本次未执行。
- 阻塞：由于环境或依赖问题无法完成验证。
- 未覆盖：没有适当的测试验证相关行为。

测试通过不等于代码审查通过，也不等于整个项目已经验收完成。
