# 需求记录

此目录是项目长期需求基线，随 Git 版本管理，不是会话临时文件。

## 结构

- 每条可独立验收的业务规则使用稳定 ID，并单独保存为 `REQ-<DOMAIN>-<NUMBER>.md`，例如 `auth/REQ-AUTH-001.md`。
- 变更编号为 `CHG-YYYYMMDD-NNN`；创建前由总控检查仓库现有记录及待合并改动，再串行分配，同一日期序号递增。若合并前发现冲突，先协调并重编号再合并。日期取记录时间在 `Asia/Shanghai` 的本地日期。一条变更可关联多个需求 ID。
- 复制 `templates/requirement.md` 和 `templates/change.md` 创建记录。

## 记录规则

- 需求文件描述当前已确认、有效的规则；一个文件只记录一条可独立验收的原子规则。新需求可先建为 `proposed`，但其规则是拟议内容，不是有效基线；既有需求变更先写入变更记录，原有效修订保持不变。只有关联变更状态为 `approved` 且具备用户明确肯定答复或可核验正式批准的记录，才可更新需求文件中的有效规则和修订号。`pending`、`rejected` 或不确定/无法核验的答复均不得改变基线。批准后，新需求才转为 `active`；既有需求的修订才切换为新有效修订，旧修订按需标为 `superseded` 或 `withdrawn`。
- 每条变更记录说明提出内容、提出时间、记录时间、来源、原因、受影响需求、变更前后规则、影响和决定。变更记录只追加；状态变化作为带时间和责任人的新处理记录追加，不改写或删除已有历史。处理记录中的状态必须与变更记录当前 `status` 快照完全一致，且仅使用 `pending`、`approved`、`rejected`。快照改变时，同一条追加事件须记录新状态、时间、处理人、用户决定人、决定时间、可追溯证据及决定说明。更正也新建变更记录并引用原记录。
- `requested_at` 是客户提出时间，`recorded_at` 是实际写入时间；两者以及已知的用户决定时间，均使用带 UTC 偏移的 RFC 3339 时间戳并记录对应 IANA 时区。未提供提出时间或决定时间时记为 `unknown`，不得编造；时间没有时区时先向用户确认，不能确认则标记未知。记录时间必须填写。
- 未确认规则保持 `pending`，不得作为实现依据。只有用户明确肯定答复或可核验正式批准，且记录决定人、决定时间与证据后，才可更新需求文件中的当前有效规则和修订号；不确定答复不得改变基线。
- Git diff/commit 补充记录文件的修改历史；`git_ref` 可在相关提交存在后填写。Git 记录不能替代变更记录中的业务原因、前后规则和用户决定。

## 状态

需求状态：`proposed`、`active`、`superseded`、`withdrawn`。`proposed` 内容不是有效基线；只有关联变更为 `approved` 且记录明确、可核验的用户批准后，才可设为 `active` 并生效。既有需求在新修订获批前维持原 `active` 基线。

变更状态：`pending`、`approved`、`rejected`。当前 `status` 字段是最新状态快照；处理记录中的每条状态必须使用同一枚举。每次快照改变时，在追加事件中同步记录该状态及时间、处理人、用户决定人、决定时间、可追溯证据和决定说明。`approved` 必须对应用户明确肯定答复或可核验正式批准；否则保持 `pending`，不得更新需求基线。
